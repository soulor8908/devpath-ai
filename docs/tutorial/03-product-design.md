## 3.1 四层架构（产品的骨架）

devpath-ai 的产品架构建立在四层之上，每层解决一个明确的问题。这是乔布斯视角的"聚焦"——每层只做一件事，做到极致。

```
┌─────────────────────────────────────────────────────────────┐
│  L4 交付层（已有，保留）                                          │
│  FSRS 复习 · 番茄钟 · 节奏引擎 · 情绪能量 · 成就系统 · 学习队列    │
│  → 职责：解决"坚持"和"记忆"                                     │
├─────────────────────────────────────────────────────────────┤
│  L3 验证层（V1-V4 状态机）                                       │
│  V1 FSRS 卡片 · V2 代码沙箱 · V3 AI 按 Rubric 审 GitHub 仓库 ·   │
│  V4 作品集发布到 /portfolio + 公开展示                            │
│  → 职责：解决"学会了吗"的客观验证                                │
├─────────────────────────────────────────────────────────────┤
│  L2 路径引擎（lib/curriculum/path-engine.ts）                   │
│  技能图谱 + 迁移映射 + Kahn 拓扑排序 + 时间约束 → 个性化路径      │
│  → 职责：解决"下一步学什么"                                      │
├─────────────────────────────────────────────────────────────┤
│  L1 内容层（content/ YAML，护城河）                              │
│  策展式知识库：技能图谱 · 权威来源 · 代码实验 · 坑点库 · Rubric   │
│  Content-as-Code，版本化，可审查                                 │
│  → 职责：解决"学什么"和"凭什么信你"                              │
└─────────────────────────────────────────────────────────────┘
```

### 3.1.1 L1 内容层（护城河）

**乔布斯视角**：健身房再豪华也没用，关键看里面有没有训练计划。DevPath 的学习内容不是 LLM 现场生成的二手货，而是仓库里 YAML 代码版本化的策展知识图谱。

**核心设计**：
- **Content-as-Code**：知识库不是数据库里的行，是仓库里的代码。`content/graph/nodes/*.yaml` 49 个技能节点，覆盖 LLM / RAG / Agent / 工程 / Python / Prompt 等九大类。
- **权威来源等级**：每个节点必须挂载 ≥2 条 T0-T2 级权威来源（官方文档 / 论文 / 经典源码 / 一线工程博客），不允许 LLM 即兴生成。
- **三层质量门禁**：结构层（zod schema）+ 图谱层 G1-G7（前置存在 / 来源已登记 / ≥1 T0-T1 / 无环 / 轨道阶段合法 / V3-V4 必挂 Rubric / 权重和=100）+ 成分层（权威体系 / 教学完备 / 路径引擎端到端）。

**为什么这样设计**：2026 年 LLM 生成的二手内容无限供应且持续贬值，有出处的一手内容反而升值。知识库的每一条内容必须能回答："这句话的依据是什么？出处在哪？"

**节点 Schema 示例**（简化版，完整版见 [docs/curriculum-content.md](file:///workspace/docs/curriculum-content.md)）：

```yaml
id: rag.chunking-strategies
title: 分块策略
track: [frontend-to-ai-engineer]
prerequisites: [llm.embeddings, rag.pipeline-overview]
frontend_bridge: |            # 迁移映射
  你写过虚拟列表的窗口化渲染——分块就是给文本做窗口化
concepts: [...]               # 核心概念
authoritative_sources:        # 权威来源，必填，至少 2 条
  - { type: official-doc, ref: "sources/registry.yaml#langchain-text-splitters" }
  - { type: engineering-blog, ref: "sources/registry.yaml#pinecone-chunking" }
gotchas: [...]                # 坑点（来自真实工程经验）
interview:                    # 面试题（入库，非实时生成）
  - { q: "...", answer_skeleton: "...", followups: [...] }
mastery_check:                # 可执行验证
  type: code-challenge
  rubric: projects/rubrics/chunking.yaml
```

### 3.1.2 L2 路径引擎（个性化最短路径）

**乔布斯视角**：前端工程师不是零基础——TypeScript、异步、HTTP、组件化思维全部是可迁移资产。不利用迁移的路径设计就是浪费用户时间。

**核心设计**：
- **Kahn 拓扑排序**：从技能图谱生成合法学习顺序，同层按 phase/id 字典序保证产物确定性
- **跳过已掌握**：基于用户画像自动跳过 `skillLevel=advanced 且 stability>21天` 的节点
- **6 个预置轨道**：前端转 AI（旗舰 49 节点）/ 算法 200 / 前端 / 后端 / AI / LLM 应用
- **可行性评分**：confidence < 0.5 自动降级（减少每日新学量）

**为什么这样设计**：学习效率 = 路径优化问题。给定目标技能图 G 和当前技能集合 S₀，最优路径是 G 的拓扑排序中跳过 S₀ 已覆盖节点的最短路径。

### 3.1.3 L3 验证层（V1-V4 状态机）

**乔布斯视角**：Skills are built by doing, not by reading。学习的最小单元是项目，文章只是项目的说明书。

**4 级验证（逐级递进，不可跳级）**：

| 级别 | 形式 | 验证什么 | 状态 |
|---|---|---|---|
| V1 | FSRS 卡片 | 概念理解 | ✅ 已有 |
| V2 | 沙箱代码题 | 能写出来 | 🚧 进行中 |
| V3 | 项目检查点（AI 按 Rubric 审 GitHub 仓库） | 能造出来 | ✅ 已有 |
| V4 | 作品集发布 | 能证明给谁看 | ✅ 已有 |

**为什么这样设计**：神经层面，"看懂"和"会做"是两套回路。会做 = 在真实约束下做过决策、踩过坑、调试过失败。代码要么跑通要么报错，测试要么过要么不过——这是编程学习区别于其他学科的最大优势：验证可以自动化。

### 3.1.4 L4 交付层（坚持与记忆）

**乔布斯视角**：人坚持不下去不是因为懒，是因为看不到自己在接近"成为某种人"。产品必须让进度外显为证据。

**核心设计**：
- **FSRS 复习**：基于遗忘曲线的科学调度（ts-fsrs 4.5），3 种参数预设（conservative 0.95 / standard 0.9 / aggressive 0.8）
- **番茄时钟**：25min 专注 + 5min 休息 + 4-1 长休息规则，浮动 widget 两态（ring 56px ↔ card 280px）
- **节奏引擎**：6 条决策优先级链统一编排"现在该做什么"，不消耗 AI 额度
- **能量回归**：8 维特征线性回归预测次日容量，每周自动重训练
- **情绪觉察**：1 秒记录情绪 + 多巴胺干扰来源
- **成就系统**：16 个预置成就，纯函数检测
- **学习队列**：合并"新学"+"复习"为单一待办流，5 维评分

**为什么这样设计**：遗忘是默认值，间隔重复是唯一的对抗手段。靠意志力坚持的学习产品留存率不到 10%，需要的是机制设计。

## 3.2 6 条产品原则（乔布斯视角）

引用自 [docs/PRODUCT.md](file:///workspace/docs/PRODUCT.md) "核心产品原则" 章节，每条配乔布斯视角的解读。

### 原则 1：内容是护城河，不是机制

> 「健身房再豪华也没用，关键看里面有没有训练计划。」

**乔布斯解读**：Duolingo 值钱的地方不是 Streak 机制——那玩意谁都能抄——而是它几千节被精细编排过的课程。多邻国的 Streak 之所以有效，是因为课程本身值得坚持。

DevPath 的学习内容不是 LLM 现场生成的二手货，而是仓库里 YAML 代码版本化的策展知识图谱。每条节点都能回答：「这句话的依据是什么？出处在哪？」。LLM 是导师，不是教材本身。

### 原则 2：Skills are built by doing, not by reading

**乔布斯解读**：神经层面，"看懂"和"会做"是两套回路。学习的最小单元是项目，文章只是项目的说明书。所以 DevPath 强制每个知识节点挂 V2 代码沙箱 + V3 项目检查点，AI 按 Rubric 审你的真实 GitHub 仓库。

### 原则 3：路径是个性化的最短路径

**乔布斯解读**：前端工程师不是零基础——TypeScript、异步、HTTP、组件化思维全部是可迁移资产。DevPath 用技能图谱 + 拓扑排序 + 用户画像自动跳过已掌握节点，不浪费你一分钟。

### 原则 4：权威 = 策展，不是生成

**乔布斯解读**：2026 年 LLM 生成的二手内容无限供应且持续贬值，有出处的一手内容反而升值。DevPath 的知识库每条内容必须挂载 T0（官方文档/论文）或 T1（经典源码/Cookbook）级权威来源，T3 二手解读仅作补充不可单独支撑节点。

### 原则 5：动力 = 朝向身份的可见进展

**乔布斯解读**：人坚持不下去不是因为懒，是因为看不到自己在接近"成为某种人"。DevPath 把进度外显为证据：可部署的项目、GitHub 仓库、`/portfolio` 可分享作品集、`/u/<username>` 公开学习轨迹。学习轨迹本身就是求职资产。

### 原则 6：坚持是设计出来的，不是靠意志力

**乔布斯解读**：番茄钟 25min 专注 + 5min 休息 + 4-1 长休息规则；节奏引擎 6 条决策链告诉你「现在该做什么」；能量回归模型预测你明天的容量，自动降级过载日程；情绪觉察识别多巴胺干扰，AI 给出应对建议；成就系统 16 个徽章正向激励。

## 3.3 与竞品的差异

### 3.3.1 差异矩阵

| 维度 | DevPath | 普通学习网站 | AI 聊天工具 | 刷题平台 |
|---|---|---|---|---|
| 内容来源 | 仓库 YAML 策展 + T0-T2 权威来源 | UGC / 编辑整理 | LLM 即兴生成 | 题库 |
| 路径个性化 | 技能图谱 + 拓扑排序 + 跳过已掌握 | 固定课程 | 无 | 无 |
| 验证闭环 | V1 FSRS → V2 沙箱 → V3 项目审 → V4 作品集 | 选择题 / 测验 | 无 | 算法题 |
| 坚持机制 | 番茄 + 节奏引擎 + 能量回归 + 情绪 + 成就 | Streak | 无 | Streak |
| AI 角色 | 编排器（Persona + 画像 + 工具调用） | 无 / 辅助 | 主功能 | 无 |
| 输出证据 | GitHub 仓库 + 作品集 + 公开主页 | 证书 | 无 | 通过率 |
| 数据归属 | 本地 IndexedDB + 可选 KV 同步 | 平台服务器 | 平台服务器 | 平台服务器 |

### 3.3.2 为什么是"教练"而非"工具"

**乔布斯视角**：工具是被使用的，教练是陪伴的。

| 维度 | 工具思维 | 教练思维（DevPath） |
|---|---|---|
| 交互模式 | 用户主动找功能 | 教练主动告诉你"现在该做什么"（节奏引擎） |
| 反馈方式 | 被动等用户操作 | 主动识别状态（能量低 / 情绪差 / 断卡）+ Persona 切换 |
| 个性化 | 千人一面 | 用户画像 6 维 + 24h TTL 自动重建 + 高频维度事件驱动增量更新 |
| 进度感 | 完成任务 | 朝向身份的可见进展（GitHub 仓库 + 作品集 + 公开主页） |
| 失败处理 | 用户自己扛 | 温和陪伴 Persona + 断卡恢复成就 + AI 应对建议 |

### 3.3.3 4 种 Persona（教练的"人格"）

DevPath 的 AI 教练不是千人一面，会根据用户状态自动切换人格：

| Persona | 触发条件 | 风格 |
|---|---|---|
| 严厉教练 | energy≥4 + 计划滞后 | 推你一把，不容懈怠 |
| 温和陪伴 | energy≤2 + mood=bad | 理解你的低落，建议休息 |
| 苏格拉底导师 | topic 含代码/算法/原理 | 不直接给答案，引导你思考 |
| 平等同行 | 默认 | 像朋友一样讨论 |

用户也可以在"我的 → Persona"手动覆盖。

## 3.4 设计哲学：从"功能堆砌"到"策展护城河"

### 3.4.1 初版的问题（功能堆砌）

引用自 [devpath-ai-redesign.md](file:///workspace/devpath-ai-redesign.md) 第一部分：

> **现在的 devpath-ai 是一个寻找内容的学习引擎。重构的方向：把它变成一个有引擎的课程体系。**

初版的 4 个问题：
1. **通用 = 无定位**："告诉 AI 你想学什么"是工具定位，不是产品定位
2. **AI 生成内容没有权威层**：质量不可验证、内容无出处、错误无追责
3. **没有能力验证闭环**：只验证"记住了吗"，不验证"能造出来吗"
4. **机制过剩，内容贫血**：给自行车装飞机引擎

### 3.4.2 重构方向（策展护城河）

**乔布斯视角的减法**：
- 从"想学什么都行"收窄到"前端转 AI 旗舰路径"
- 从"AI 实时生成"改为"策展式 YAML + AI 当导师"
- 从"记住就好"升级到"V1-V4 验证闭环"
- 从"机制过剩"转为"内容是护城河"

### 3.4.3 现有代码的去留决策

| 现有模块 | 决策 | 理由 |
|---|---|---|
| FSRS / 番茄钟 / 节奏引擎 / 优先级引擎 | **保留** | 这是交付层，正好是别人没有的 |
| RAG 知识检索（向量 + 降级） | **保留并扩大** | 基础设施复用，索引内容换成策展知识库 |
| AI 现场拆知识树 | **降级为辅助** | 旗舰路径用策展图谱；AI 拆树只用于非旗舰的自定义主题 |
| AI 生成面试题 | **改造** | 题目进库、人工/AI 双审、标注出处，不再实时裸生成 |
| 能量/情绪/成就 | **保留** | 留存机制，原理 3 和 6 的支撑 |
| 公开主页 /u/[username] | **升级为作品集** | 从"学习轨迹"升级为"能力证据" |

## 3.5 日常使用闭环（产品设计落地）

```
每天打开 devpath-ai
   │
   ├─ 首页 Hero 区：节奏引擎告诉你「现在该做什么」
   │   ├─ 继续专注 → 启动番茄钟（25min 专注 + 5min 休息）
   │   ├─ 低能量 → 休息建议
   │   ├─ 到期复习 → 跳转复习页（FSRS 调度卡片）
   │   ├─ 学习时段 → 跳转学习页（当日新学任务）
   │   └─ 接近睡觉 → 睡前复盘
   │
   ├─ KPI 三宫格：今日清单 N 项 / 已完成 X 项 / 连续打卡 N 天
   ├─ AI 教练洞察区：用户画像 + 能力雷达 + AI 质量摘要
   ├─ 能量趋势迷你图 + 7 天热力图
   └─ 今日学习队列：5 维评分排序的新学+复习合并待办流
       ↓
       跳转用 buildSceneUrl 携带场景参数（planId/nodeId/cardId/date）
       ↓
   学习/复习页聚焦到目标任务，无需重新查找
```

**乔布斯视角的细节**：
- 首页只有 6 区（Hero / KPI / AI 洞察 / 能量 / 热力图 / 学习队列），每多一区都是认知负担
- 底部导航只有 4 项，不是 5 项（聊天从 tab 改为浮动入口）
- 番茄钟 widget 只有 ring/card 两态，不是全屏 modal
- 跳转携带场景参数（AGENTS.md 2.12 强制），用户落到目标页不用重新找

## 本章小结

**学到了什么**：
1. 四层架构：L1 内容（护城河）/ L2 路径（最短路）/ L3 验证（V1-V4）/ L4 交付（坚持与记忆）
2. 6 条产品原则：内容是护城河 / Doing / 个性化最短路 / 权威=策展 / 朝向身份 / 坚持是设计
3. 与竞品差异：教练而非工具 / 4 种 Persona / 数据归用户 / V1-V4 验证闭环
4. 设计哲学：从"功能堆砌"到"策展护城河"的减法重构

**关键决策回顾**：
1. 内容策略：Content-as-Code（YAML + 权威来源 + 三层质量门禁）
2. 验证策略：V1-V4 四级状态机（不可跳级）
3. AI 角色：编排器（Persona + 画像 + 工具调用），不是主功能
4. 减法重构：从"想学什么都行"到"前端转 AI 旗舰路径"
