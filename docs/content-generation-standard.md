# AI 内容生成规范（知识点 / 题目 / 答案）

> **地位**：所有 AI 生成知识库内容的强制规范——包括本项目运行时生成（`lib/ai/prompts.ts`）、
> 策展轨道批量生产（`content/graph/nodes/*.yaml`，人工或子代理编写）、以及任何未来新增的
> 内容生成入口。
> **守护**：`lib/ai/prompts.ts` 前置注入 + `__tests__/content-generation-standard.test.ts`
> + `docs/code-audit-methodology.md` 定期审计。三层缺一不可。
> **优先级**：内容质量规则以本文件为准；节点结构/来源等级规则见
> [curriculum-content.md](file:///workspace/docs/curriculum-content.md)。

---

## 0. 为什么有这份规范

2026-07-26 用户反馈：AI 生成的知识库"知识点不够全面、题目太少、答案太简单，让人觉得
候选人知识浮于表面、只是背题，直接就被淘汰了"。

根因不是模型能力，而是**生成约束太松**：旧 prompt 只要求"三段式、200-500 字"，没有要求
实战案例、量化数字、踩坑叙事——模型自然输出教科书式安全答案。

**教训：AI 对内容负责的前提是，"合格"被写成了可检查的规则。** 本规范把"合格"定义为
四个可机器/人工检查的标准：结构、量化、叙事、对照。

---

## 1. 生成流程（六步，缺一不可）

任何批量内容生产任务（含子代理）必须按此流程：

1. **盘点现状**：先统计现有节点数/题数/薄弱答案，定位缺口，再决定补什么。
   禁止不看现状直接生成。
2. **调研高频考点**：以一手来源为准（官方文档/规范/论文/一线工程博客），
   禁止仅凭训练记忆编造"经验值"。经验值必须标注适用条件
   （反例：旧内容写"中文 token 消耗 1.5-2 倍"——这是旧分词器经验值，
   正确写法是注明分词器 cl100k_base/o200k_base 并给出实测方法）。
3. **按第 3-5 节规范生成**。
4. **自检**（第 6 节清单，机器可跑的部分必须跑）。
5. **守护测试全绿**：`npm run content:validate` + `npm test`。
6. **同步远程**：提交并推送到**用户选择的分支**（不是工具自动创建的分支）。

## 2. 知识点规范（knowledge node / 知识树拆解）

### 2.1 正确性

- 每个事实性陈述必须能被一手来源（T0/T1，见 curriculum-content.md）佐证。
- 区分**事实**与**经验值**：经验值必须带适用条件与量级（如"HNSW 图退化"必须说明
  触发条件是高频删除/更新产生墓碑节点，而非泛泛"频繁增量后退化"）。
- 拿不准的表述降级为区间或机制描述，禁止编造精确数字。

### 2.2 完整性

- 覆盖该主题在面试中的主要考察面；重要考点不得遗漏（宁多勿缺后裁剪，勿先漏后补）。
- 节点依赖（prerequisites）必须闭环，引用存在的节点。
- `bigTech` / 难度标定基于**真实面试频率**，不凭主观印象。

### 2.3 前端映射（本轨道特有）

面向"前端工程师 → AI 工程师"轨道的内容，每个节点必须有 `frontendBridge`：
用前端已有心智（缓存/状态机/SSE/组件化/XSS 防御等）类比新概念，降低迁移成本。

## 3. 题目规范（interview question）

### 3.1 角度分布

每个知识点的题目必须覆盖四个角度（4 题时一角一题）：

| 角度 | 问什么 | 例 |
|------|--------|-----|
| 概念辨析 | A 和 B 的本质区别、各自适用边界 | "微调 vs RAG 的决策框架" |
| 原理深挖 | 内部机制、为什么这样设计 | "LoRA 为什么省显存？省的是什么？" |
| 实战设计 | 给一个场景让候选人设计系统 | "设计客服场景的多模型路由" |
| 踩坑对比 | 失败模式、事故、修复过程 | "微调后怎么发现灾难性遗忘？" |

### 3.2 题面质量

- 题面必须**具体、有工程场景感**。禁止"什么是 X""谈谈你对 X 的理解"这类泛泛题。
- 同一知识库内题面不得重复（trim + 大小写不敏感）。
- `followups` 2-3 条，必须是面试官真实会追问的深挖问题，可加提示性括号。

---

## 4. 答案规范（核心中的核心）

### 4.1 四段式结构（强制）

每道面试题的答案必须按四段式组织，400-600 字（运行时生成为 400-700 字）：

1. **【分层原理】**：不是名词定义，是机制解释——"为什么这样设计、内部发生了什么"。
   含量化细节（具体数字、量级、百分比）。
2. **【实际案例】**：第一人称项目案例（"我在 XX 项目里…"），**必须含具体数字**
   （延迟 ms、成本 $、准确率 %、命中率 %、bad case 率、数据规模），
   且包含**踩坑→修复**过程（"第一次翻车是因为…后来改成…"）。
3. **【举一反三】**：把该知识推广到其他场景，或与读者的工程经验做映射
   （本轨道读者是前端：缓存/状态机/SSE/表单校验/XSS 防御等）。
4. **【扣分点对照】**：明确写出"只会背概念的回答长什么样 vs 真正做过的人怎么答"。
   这段是让答案产生"面试官信任"的关键。

### 4.2 反模式黑名单（命中即不合格）

- 名词罗列："X 有 A、B、C 三个特点"而无机制解释
- 教科书句式："X 是一种 Y 的技术，广泛应用于 Z"
- 空洞案例：号称"项目中用过"但无任何数字、无踩坑过程
- 经验值无前提：不给适用条件的"一般是""通常是"
- 占位符：`待补充` / `TODO:` / `FIXME:` / `lorem ipsum` 等
  （由 `__tests__/preset-content-quality.test.ts` 机器拦截）

### 4.3 运行时生成的特别约束

- 批量并发路径（`question_stem_generate`）只产题干，答案由单题流式路径
  （`answer_generate`）生成——大 JSON 输出在批量并发下会截断/限流（2026-07-26 事故），
  新入口必须沿用"批量小输出 + 单题大输出"的拆分。
- 流式答案路径的输出长度上限可以放宽，但**四段式结构不得因流式而省略**。

## 5. 注入点（运行时强制）

| 生成入口 | 文件 | 注入内容 |
|----------|------|----------|
| 知识树拆解 | `lib/ai/prompts.ts` `knowledge_decompose` | 第 2 节（正确性/完整性） |
| 题干生成 | `lib/ai/prompts.ts` `question_stem_generate` | 第 3 节（角度/题面质量） |
| 完整题目生成 | `lib/ai/prompts.ts` `question_generate` | 第 3 + 4 节 |
| 答案生成 | `lib/ai/prompts.ts` `answer_generate` | 第 4 节 |

共享约束收敛在 `lib/ai/prompts.ts` 的常量中（单一事实源），各 prompt 拼接注入。
修改任何 prompt 必须 bump version（`__tests__/prompts.test.ts` 指纹快照强制）。

---

## 6. 自检清单（生成后必跑）

机器可跑（批量生产任务必须执行到全绿）：

```bash
npm run content:validate   # YAML/schema/产物新鲜度
npm test                   # 含内容质量门禁 + prompt 指纹快照
npm run typecheck && npm run lint
```

人工/子代理自查（逐条回答是）：

- [ ] 每题答案是否四段式齐全？【实际案例】是否有至少 2 个具体数字？
- [ ] 数字是否符合工程常识（量级不错乱）？
- [ ] 每节点四题是否覆盖概念/原理/实战/踩坑四角度、互不重复？
- [ ] 经验值是否都标注了适用条件？
- [ ] followups 是否是面试官真会追问的问题（而非"你怎么看"式水追问）？
- [ ] 把答案给一个资深工程师看：他会认为这是"做过的人"还是"背题的人"？

## 7. 追责机制（"为生成的内容负责"如何落地）

1. **前置约束**：第 5 节注入点保证运行时生成天然带规范约束。
2. **CI 守护**：`content-generation-standard.test.ts` 拦截"删约束"行为；
   `preset-content-quality.test.ts` 拦截占位符/裸答案/孤儿题；
   `prompts.test.ts` 指纹快照拦截"改 prompt 不留痕"。
3. **定期审计**：`docs/code-audit-methodology.md` 多轮深度审计，
   内容维度按本规范第 4 节逐项核查。
4. **版本可归因**：每次 AI 调用记录 `promptVersion` 指纹
   （`AICallRecord.promptVersion`），内容质量问题可回溯到具体 prompt 版本。

---

## 8. 更新本文件

内容质量标准演进时，必须同步：本文件 + `lib/ai/prompts.ts` 注入常量
+ `__tests__/content-generation-standard.test.ts` 守护断言。
**规则没有注入等于不存在，注入没有测试守护等于建议。**
